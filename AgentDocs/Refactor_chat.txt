Thought for 30s
Yes — but only for logs/events, not for arbitrary “contract was updated” state changes.

What the block header bloom can tell you
eth_getBlockByNumber or eth_getBlockByHash returns a block object that includes logsBloom, a 256-byte bloom filter for the logs emitted in that block. Ethereum’s RPC docs explicitly list logsBloom as “the bloom filter for the logs of the block,” and eth_getBlockByNumber returns the same block object format as eth_getBlockByHash.

So you can check the bloom for:

Your contract address
Meaning: “Did any log in this block originate from this contract?”

A specific event topic
Meaning: “Did any log in this block possibly include this event signature?”

That gives you a fast prefilter:

block header logsBloom
    contains contract address?
    contains event signature topic?
        yes -> fetch logs / receipts and verify exactly
        no  -> skip block
This lines up with the existing evmrelay architecture notes: filter block/header bloom first, then fetch receipts/logs only when the bloom matches; final verification checks log.address == contract and topics[0] == event_signature.


What it cannot tell you
The bloom does not tell you that contract storage changed, code changed, or that a function was called unless the contract emitted a log/event for that action.

A contract call like:

setBridgeAddress(address newBridge)
will not appear in logsBloom unless the function emits something like:

event BridgeAddressUpdated(address indexed oldBridge, address indexed newBridge);
Then the bloom can catch:

contract address
topic0 = keccak256("BridgeAddressUpdated(address,address)")
possibly indexed parameter topics
But bloom filters have false positives, so a match only means “possibly present.” You must still fetch logs with eth_getLogs or receipts and check the actual log fields. Ethereum’s eth_getLogs supports filtering by block range/hash, contract address, and ordered topics, which is the precise verification step.

What about “certain call in it”?
There are two different cases:

Event-based detection:
Yes. If the function emits a unique event, check the block logsBloom for:

contract address
topic0 = keccak256("EventName(type1,type2,...)")
optional indexed topics
Then call eth_getLogs for that block.

Function-call detection:
Not from the bloom. For that, you need to inspect transactions in the block. Call eth_getBlockByNumber(block, true) so full transaction objects are returned, then scan:

tx.to == yourContract
tx.input[0:4] == functionSelector
The JSON-RPC docs show that full transaction objects include to and input, where input is the method selector plus ABI-encoded parameters.

Best architecture
For your watcher, I’d use this layered approach:

1. Get block header / block object.
2. Check logsBloom for contract address + event signature.
3. If bloom misses, skip receipt/log fetching.
4. If bloom matches, call eth_getLogs for that exact block:
   - address: your contract
   - topics[0]: event signature
5. If you also care about direct function calls:
   - get full block transactions
   - scan tx.to and tx.input selector
6. Treat logs/events as authoritative for “contract updated.”
The important distinction is:

logsBloom = fast event/log prefilter
transactions/input = function-call detection
state diff/storage proof = actual state-change detection
So yes, this is a good optimization for your relay, especially for avoiding unnecessary receipt requests. Just design the contracts to emit explicit events for every state update you care about.

Startup catch-up with RPC
Yes, a starting node can use RPC to find missed blocks with bloom matches.

The basic catch-up algorithm would be:

lastProcessedBlock = local checkpoint + 1
safeHead/finalizedHead = ask RPC

for blockNumber in [lastProcessedBlock ... targetHead]:
    block = eth_getBlockByNumber(blockNumber, false)
    if block.logsBloom possibly contains watched contract + event topic:
        logs = eth_getLogs({
            fromBlock: blockNumber,
            toBlock: blockNumber,
            address: watchedContract,
            topics: [watchedEventTopic]
        })
        process exact logs
eth_getBlockByNumber accepts an integer block number or tags like "latest", "safe", and "finalized", and returns a block object that includes logsBloom.
 eth_getLogs can then filter by fromBlock, toBlock, address, topics, or blockHash, with topics being order-dependent.

So yes, you can do a header-bloom pre-scan over block numbers through RPC.

But there is an even simpler RPC catch-up
For RPC, you often do not need to manually scan every block’s bloom. You can just call:

{
  "method": "eth_getLogs",
  "params": [{
    "fromBlock": "0xSTART",
    "toBlock": "0xEND",
    "address": "0xYourContract",
    "topics": ["0xYourEventTopic0"]
  }]
}
Internally, the node uses its indexes / bloom filtering to avoid brute-force receipt scans. That is usually simpler and faster than fetching every block yourself.

The reason to manually fetch each block and check logsBloom first is mainly if you want:

- exact control over per-block processing
- lower eth_getLogs range size
- rate-limit friendliness
- deterministic checkpointing
- compatibility with providers that limit eth_getLogs ranges
- parity with your P2P/light-client path
A good hybrid is:

1. Split catch-up into ranges, e.g. 500 / 1000 / 5000 blocks.
2. Use eth_getLogs for each range.
3. Store last processed finalized/safe block.
4. If provider limits ranges or logs are too heavy, fall back to block-by-block logsBloom prefilter.
About waiting for confirmations vs finalized
For Ethereum mainnet, RPC supports "safe" and "finalized" block tags. "latest" is the newest proposed block, "safe" is the latest safe head, and "finalized" is the latest finalized block according to the JSON-RPC block parameter docs.

So if the RPC provider supports it, you can do:

eth_getBlockByNumber("finalized", false)
Then use that block number as your catch-up target. That avoids guessing “N confirmations” on Ethereum.

For Polygon, BSC, and Base, support and semantics of "safe" / "finalized" can vary by provider and chain. I would implement this strategy:

1. Try "finalized".
2. If unsupported, try "safe".
3. If unsupported, use latest - chainConfirmations.
Suggested defaults:

Ethereum: prefer finalized; otherwise latest - 64
Base: prefer finalized/safe if provider supports it; otherwise latest - conservative delay
Polygon: use latest - N confirmations unless you separately verify checkpoints
BSC: use latest - N confirmations, probably a small but nonzero depth
For a bridge-style system, I would not process latest as final. It is fine for early detection, but not for releasing value.

The block bloom can only say:

  - this emitting contract address
  - this event topic
It can never say “definitely contains.” Bloom filters can have false positives. So the correct test is:

if bloom_maybe(contractAddress) && bloom_maybe(eventTopic0):
    fetch logs/receipts
    verify exact log.address and topics[0]
else:
    skip
For your use case — “just looking for a logged message in particular” — that is ideal.

The architecture I’d use:

1. Edge ETHWatch nodes
   - Run RLPx/devp2p where possible.
   - Optionally use RPC/WebSocket fallback.
   - Watch only GNUS bridge event logs.
   - Produce validator vote evidence.

2. Proposal layer
   - Edge node sees BridgeSourceBurned / BridgeMessage event.
   - It builds a canonical observation:
       chainId
       blockHash
       blockNumber
       txHash
       logIndex
       contract
       topic0
       topics[]
       data
       decoded fields
   - It signs the observation.

3. Verification layer
   - Other edge/reputation nodes receive the proposed txHash/logIndex.
   - They can independently fetch eth_getTransactionReceipt from free RPC.
   - They verify:
       receipt.status == 1
       receipt.blockHash == proposed blockHash
       receipt.logs[logIndex].address == contract
       receipt.logs[logIndex].topics[0] == expected event
       decoded event fields match proposal

4. Consensus certificate
   - GNUS consensus aggregates signatures/votes.
   - Certificate says: “This source-chain event is accepted.”
   - Dedupe key:
       srcChainId + txHash + logIndex

5. Mint / release function
   - Destination mint function accepts the certified message.
   - It verifies the GNUS certificate.
   - It checks the event has not already been consumed.
   - It mints/releases.
One important correction in the wording: the light node should not just get the ethTransaction. It should get the transaction receipt or at least a normalized event proof derived from the receipt. The transaction proves “someone called something.” The receipt proves “the call succeeded and emitted this log.” For a bridge, the receipt/log is the security object.

This is better than making the Ethereum receipt proof directly verifiable on-chain, because EVM receipt proofs are painful and chain-specific. Instead, the destination chain trusts the GNUS consensus certificate, and GNUS consensus is responsible for verifying the source event.

I’d think of it as two security tiers:

Tier 1: Detection
  RLPx edge ETHWatch sees events without centralized RPC.

Tier 2: Confirmation

  including free RPC, paid RPC, own nodes, or RLPx receipts.

Tier 3: Certification
  GNUS consensus signs/finalizes the normalized event.

Tier 4: Execution
  Destination mint contract verifies the GNUS certificate.
That lets you use RLPx where it is valuable — decentralized edge observation — without forcing every validator or every client to implement the full Ethereum wire protocol.

Yes — that is exactly why I’d keep the RLPx/ETH protocol code isolated behind an upgradeable edge-watcher module, not embedded into bridge consensus or minting logic.

The right mental model is:

Edge watcher transport can change.
Bridge event format should not change.
Consensus certificate format should change rarely.
Mint verification should change almost never.
Ethereum wire protocol versions and fork rules will keep changing. The official devp2p spec currently describes eth as running over RLPx and, in the version I found, says the current protocol version is eth/70; it also notes that after The Merge, block propagation is no longer handled by the eth protocol and that NewBlock/NewBlockHashes style propagation is legacy/defunct for PoS Ethereum.
 So yes: if you depend directly on eth/68, eth/69, eth/70, future eth/71/eth/72, etc., you need a transition strategy.

1. Transport adapter version

This changes when you change quorum rules, signature aggregation, BLS keys, validator set commitments, or reputation weighting.

Fork handling
Ethereum block headers already evolve with forks. The devp2p spec shows this directly: headers include fields such as basefee-per-gas, withdrawals-root, blob-gas-used, excess-blob-gas, parent-beacon-root, and requests-hash, with presence/absence depending on London, Shanghai, Cancun, and Prague-era forks.

So your RLP header decoder should not be a single hardcoded struct forever. I’d make it fork-aware:

class IEvmForkRules
{
public:
    virtual bool hasBaseFee(uint64_t blockNumber, uint64_t timestamp) const = 0;
    virtual bool hasWithdrawalsRoot(uint64_t blockNumber, uint64_t timestamp) const = 0;
    virtual bool hasBlobGasFields(uint64_t blockNumber, uint64_t timestamp) const = 0;
    virtual bool hasParentBeaconRoot(uint64_t blockNumber, uint64_t timestamp) const = 0;
    virtual bool hasRequestsHash(uint64_t blockNumber, uint64_t timestamp) const = 0;
};

Dual-run upgrades
When Ethereum moves to a new wire protocol or a major fork, don’t do a hard cutover. Run both watchers in parallel for a while:

Old watcher: eth/70
New watcher: eth/72

Both observe the same bridge event.
Both normalize to GNUS_BRIDGE_EVENT_V1.
Consensus only cares that the normalized claim matches.
During transition:

1. Deploy new watcher adapter.
2. Run old and new adapters side by side.
3. Compare observed txHash/logIndex/event data.
4. Mark new adapter healthy after enough matching events.
5. Move reputation weighting to new adapter.
6. Deprecate old adapter later.
The key is that consensus should not vote on “eth/72 says this.” It should vote on:

srcChainId + txHash + logIndex + decoded bridge event
The transport is just evidence collection.

Fallback model
I’d always keep at least two evidence paths:

Primary:
  RLPx edge watcher detects event.

Fallback:
  RPC/WebSocket detects event or verifies receipt.

Final:
  GNUS consensus certificate certifies event.
If eth/72 changes something or peers become unreliable, the system can temporarily rely more on RPC-backed watchers without changing the mint contract.

Mint function should stay stable
The destination mint should not know or care whether the event was discovered through RLPx, RPC, a full node, or a future Ethereum protocol.

function mintWithCertificate(
    BridgeMintMessage calldata message,
    ConsensusCertificate calldata certificate
) external {
    bytes32 messageHash = hashBridgeMintMessage(message);

    require(verifyConsensusCertificate(messageHash, certificate), "bad cert");
    require(!consumed[message.srcChainId][message.txHash][message.logIndex], "used");

    consumed[message.srcChainId][message.txHash][message.logIndex] = true;

    _mint(message.recipient, message.amount);
}
That is the correct abstraction boundary.

My recommendation
Keep RLPx, but treat it as an edge watcher plugin:

Do not make bridge consensus depend on eth/70/71/72.
Do not make mint contracts depend on Ethereum wire protocol.
Use normalized receipt/log evidence as the bridge consensus subject.
Do use consensus certificates as the stable bridge proof.
That way, when Ethereum upgrades, Polygon diverges, BSC behaves differently, or Base changes its indexing/finality assumptions, you upgrade only the watcher adapter and chain config — not the whole bridge.
